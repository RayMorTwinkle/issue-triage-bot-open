# 等待者能否拿到下一个名额？

2026-11-26 · issue-triage-bot · 本地对照实验

在一个名额被占满时，有调用已经排进队列。持有者释放名额，随即又申请一次。备份版在固定调度下连续五次让后来者抢到名额。改用按登记顺序发放的队列后，同一组操作连续五次把名额留给原等待者。旧调用在两版都最终完成，这个实验没有观测到永久饥饿或死锁。[原始基线](artifacts/before.json) · [重构复测](artifacts/after.json)

## 测什么

工单之间可以并行。闸门的配额单位是一次 Agent 调用，一张工单的三路审查会分别申请和归还。闸门作用于单个服务进程。实验运行在同一台 macOS arm64、Python 3.9.6 上，备份源码来自 `4875681a5122f48d5654dc08e32c5b7aa20880fd`，重构源码来自 `0ce1e2335cf065a47f2eaa23439da3209e8d625c`。每份运行记录包含闸门源码和实验脚本的 SHA-256。[实验脚本](artifacts/gate_probe.py)

| 固定场景 | 期望观测 | 备份 | 重构 |
| --- | --- | ---: | ---: |
| 空位与插队 | 已有等待者时，释放方立即尝试再次获取会失败 | 0/5 | 5/5 |
| 墙钟跳变 | 等待预算尚余时，调用能等到持有者释放 | 0/5 | 5/5 |
| 缩容 | 保留已运行调用，占用降到上限以下才接纳新调用 | 5/5 | 5/5 |
| 超时离队 | 等待数归零，下次申请可用 | 5/5 | 5/5 |
| 扩容 | 新开放的两个名额都能交给等待者 | 5/5 | 5/5 |
| 异常退出 | 上下文中的业务抛错后名额归还 | 5/5 | 5/5 |
| **符合预期的观测** | **同一脚本，六种场景各五轮** | **20/30** | **30/30** |

第一组用闸门内部的锁固定合法的线程交错，限制旧等待者在释放和紧接着的非阻塞申请之间重新调度。第二组只替换闸门看到的墙钟，每次读取前进一小时，操作系统时钟照常运行。这两组是定向回归样本。实验没有采集真实流量中的故障频率、模型质量、平均等待时间或吞吐量。[逐轮结果](artifacts/after.json)

## 改动与代价

原实现用条件变量广播唤醒，统计等待人数，但没有保存抵达顺序。重构后，无排队且有空位时仍直接准入。发生争用时，每个等待者登记一个共享同一把锁的条件变量。释放名额只通知队首，队首占位并离队时检查是否还有余量，以便扩容后把其余空位继续交给后继。等待预算使用单调时钟。超时和异常沿同一个清理路径移走登记项。

排序保证从登记时刻开始。同一进程内谁先拿到登记锁，仍取决于线程调度。每位排队者增加了一个条件对象，非队首取消需要在队列中定位它。队首暂时得不到调度时，后来者也会继续等。任何吞吐或尾延迟取舍都需要单独压测。

`acquire(timeout)`、`release()`、`set_limit(n)`、上下文管理器以及 `snapshot()` 的四个字段沿用原契约。服务接口、端口、提示词、模型通道与发布适配器均沿用原来的实现。

## 公开客户端与权限验证

可在公开仓打开 `docs/index.html`，编辑一张合成工单。让三路审查中负责最小改动的一路退回，观察发布和合并是否跳过。改回通过并重新运行，再比较两个审计包。每份审计包保存输入、有效档位及其来源、实际经过的环节、动作计划和停止原因。CLI 用同一规则函数复算。

私仓的继承标记为 `default`，公开客户端标为 `inherit`。实验脚本将两者映射到同一输入域。全局选五档之一，项目与单工单分别可选五档或继承，共 180 种合法组合。以工单优先、其次项目、最后全局作为预期值，备份、重构和客户端三次各得到 **180/180**。这是档位解析兼容性证据。公开客户端的三审、构建、终审均为场景输入，生产模型、身份认证与 GitHub 写入留在私仓。[输入生成器](artifacts/policy_probe.py) · [备份输出](artifacts/before-policy.json) · [重构输出](artifacts/after-policy.json) · [客户端输出](artifacts/client-policy.json)

## 全量套件与第一次失败

两份源码分别导出到临时目录，用相同解释器和隔离启动脚本运行 `unittest discover -s tests`。脚本使用干净的临时主目录，Git 只允许本地文件协议。基线 **198/198**，重构 **200/200**。新增两项检查逐个登记后的获准顺序、排队中途的超时清理。两边套件大小不同，比较闸门行为请使用上方固定脚本。[运行脚本](artifacts/run_suite.py) · [基线日志](artifacts/before-suite.log) · [重构日志](artifacts/after-suite.log)

首次在系统命令路径中完全移除 `gh` 时，备份有四项发布测试失败。其工作流结果已模拟，结束时仍会读取假仓库 `a/b` 的最新 release 标签。两次正式对照均使用同一离线命令替身，只对这一条读取返回固定标签。这里验证的是发布逻辑在模拟依赖下的行为，未执行真实发布。[首次原始日志](artifacts/before-no-gh.log)

## 复算与复跑

公开仓读者可在仓库根目录执行以下命令。第一条从逐轮观测重新汇总，并检查实验脚本指纹。第二条用本地客户端重新计算所有档位。

```sh
python3 docs/evals/artifacts/verify.py
python3 docs/evals/artifacts/policy_probe.py client . > /tmp/itb-client-policy.json
node --test tests/engine.test.cjs
node replay.cjs examples/split-review.json
```

持有私仓源码时可另开两个临时目录，使用同一个脚本复跑。第一条基线探针预期以状态 1 退出，JSON 会照常写出。基线只读导出，不需要切换分支。

```sh
work=$(mktemp -d)
mkdir "$work/before" "$work/after"
git archive 4875681a5122f48d5654dc08e32c5b7aa20880fd | tar -x -C "$work/before"
git archive 0ce1e2335cf065a47f2eaa23439da3209e8d625c | tar -x -C "$work/after"
python3 -B docs/evals/artifacts/gate_probe.py "$work/before" > "$work/before.json"
python3 -B docs/evals/artifacts/gate_probe.py "$work/after" > "$work/after.json"
python3 -B docs/evals/artifacts/run_suite.py "$work/before"
python3 -B docs/evals/artifacts/run_suite.py "$work/after"
python3 -B docs/evals/artifacts/policy_probe.py private "$work/before"
python3 -B docs/evals/artifacts/policy_probe.py private "$work/after"
```

## 面试讨论

| 视角 | 可以现场做什么 | 证据与边界 |
| --- | --- | --- |
| 产品经理 | 用同一工单演示 DRY 草稿、FULL 等待人工合并，再让一路审查退回。请维护者指出谁决定能否合并、为何停在这里。 | 对照导出包的档位来源、停止原因、动作计划。要判断是否降低维护成本，还需真实使用研究。 |
| AI Agent 开发 | 画出持有者释放、等待者被通知、后来者申请的三个时刻，再解释为什么广播无法保证顺序。 | 两组逐次失败的数据、FIFO 的定向唤醒和缩容反例，都可现场复跑。进程间分配和取消正在运行的模型请求超出此闸门职责。 |
| 后训练与评测 | 固定输入与调度条件，只替换被测实现；把原本就通过的四组控制项单列。再把一个审查意见改为缺席或退回，只观察动作计划。 | 这些是确定性规则回归样本。若评估模型分诊能力，还需独立标注的真实工单、划分训练与评测数据并复核误判。本次未开展这项实验。 |
